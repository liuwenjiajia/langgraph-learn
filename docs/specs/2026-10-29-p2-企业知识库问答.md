# P2 企业知识库问答（RAG + Ragas）

> 日期：2026-10-29（学习计划 m2-01）
> 路线：[学习蓝图](../AI智能体研发学习蓝图-6个月.md) 第 2 个月；逐日任务见 [学习计划网页](../智能体研发26周-学习计划网页.html) 的 m2-01 ~ m2-20
> 语料：`data/p2/raw/`（不入库），由 [`src/p2-rag/fetch_corpus.py`](../../src/p2-rag/fetch_corpus.py) 生成；逐页来源与官网 URL 见同目录的 `_manifest.json`

## 目标

这个知识库是学习载体，不是产品。功能做到"能问、能答、给出处、该拒就拒"为止，精力放在两件事上：

- **学 RAG**：亲手搭出 入库 → 检索 → 重排 → 生成 → 引用 五段，弄清每一段怎么影响最终答案、各自会怎么出错。
- **学 Ragas**：用它把"变好了"说成数字。范围包括四个核心指标、自定义指标、测试集生成，同时摸清它的口径、成本和局限。

做完要拿得出三样东西（对应 M2 DoD）：

| | 内容 |
|---|---|
| 能跑 | `ask.py` 回答带引用，无答案题拒答；Milvus 与 Elasticsearch 各一套可运行配置 |
| 能比 | 同一评测集上，向量 / BM25 / 混合 / +Rerank / 分块各有数字；每个优化点的收益写进 `evals/p2-rag/report.md` |
| 能评 | 在 50 条门槛集上达到三项门槛：faithfulness ≥ 0.85、无答案题全部拒答、误拒率 ≤ 10%，没达到就如实写差距；能用指标解释"为什么召回了却答错" |

## 典型用户与问题

场景设定：一家用 LangChain / LangGraph 做 Agent 的公司，研发团队把框架官方文档的固定快照当作内部知识库。拿它当"企业知识库"的替身，是因为它体量真实、术语和代码密集、相似页面多，而且答案可以核对。

| 用户 | 在做什么 | 典型问题 | 答案出处 |
|---|---|---|---|
| 应用开发（刚上手 LangGraph） | 查 API 用法和默认值 | LangGraph 默认的递归上限是多少？超了抛什么异常？ | langgraph/graph-api |
| 架构 / 选型 | 在几个方案里挑一个 | durability 的 `exit` / `async` / `sync` 三种模式怎么选？ | langgraph/checkpointers |
| 迁移维护 | 把老代码升级到 v1 | 用 `create_react_agent` 写的 agent 迁到 `create_agent`，要改哪些地方？ | migrate/langchain-v1 |
| 排障 | 拿着错误码找原因 | 报 `INVALID_CONCURRENT_GRAPH_UPDATE` 一般是什么原因？ | langgraph/errors |
| P3 研发知识助手（程序） | M3 把检索封装成子图来调用 | 同上，但要求结构化输出，方便程序继续处理 | — |

**提问约定**

- 中文提问；类名、参数名、错误码等英文术语原样保留。
- 语料是英文，所以这是**跨语言检索**：embedding 必须用多语言模型，BM25 只能靠问题里的英文术语命中。这个难点是刻意保留的，结论按题型分开看。
- 一问一答，不做多轮。

**回答约定**（`generate.py` 的输出，P3 直接复用）

- 可回答：`{answer, citations: [{source, heading_path, snippet}]}`。正文用 [1][2] 标注引用，输出用 Pydantic 校验。
- 拒答：`answer` 固定为「知识库中没有相关信息」，`citations` 为空。两种情况会触发拒答：rerank 最高分低于阈值，或者模型判断片段不足以回答。

**数据字段**：`evals/p2-rag/dataset.jsonl`，一行一题。

| 字段 | 说明 | 对应 Ragas 字段 |
|---|---|---|
| `id` | 如 `fact-001` | — |

**出题规则**

- 门槛集手写：自己挑片段，可以让模型起草，再逐条人工审改。每条都要人工确认 `reference_contexts` 能支撑 `reference_answer`。
- 无答案题分几种来源：相邻领域（如 LangSmith 定价、Ragas）、语料范围外的产品线、前提错误（问一个根本不存在的参数）。每题都要 grep 语料，确认确实找不到。
- 版本：v0 20 条（m2-06）→ v1 50 条（m2-13）。v1 定稿后冻结，之后只修客观错误（答案错、片段对不上）；改动记进 `results.md`，已有的对比行全部重跑。**不为过门槛改题、删题。**

### Ragas 对照集（不计入门槛）

对照集要回答一个问题：合成题能不能替代手写题，用来做日常回归？

| 项 | 做法 |
|---|---|
| 生成 | 用 `TestsetGenerator.generate_with_chunks` 把本项目自己切好的 chunk 喂进去，目标约 30 条。费用主要花在构建知识图谱上，大约每个 chunk 4 次 LLM 调用，生成多少条影响不大。先用 langgraph 的 38 页试跑，看过费用再决定要不要扩到全部核心文档 |
| 题型 | Ragas 只有三种合成器：单跳具体、多跳抽象、多跳具体。单跳具体大致对应事实题，两种多跳对应多片段综合题；没有对比题和无答案题 |
| 语言 | 用 `adapt_prompts("chinese", llm=..., adapt_instruction=True)` 把合成器的提示词改成中文。官方文档只演示了西班牙语，中文效果需要实测；做不到就用英文，并在结论里注明有语言差异 |
| 审核 | 不改题，只给每条打标签：合格，或不合格并写原因（问题不通顺、答案错、参考片段对不上、语料其实答不了……）。多跳题要额外看是否真的用到了多个片段：0.4.3 有已知问题，多跳具体题常常只引用一个片段 |
| 反查 | 生成结果里只有片段原文，没有 ID。按原文反查出 `source`，`recall.py` 才能在对照集上照常计算；反查不到的题只算 Ragas 指标 |
| 对比 | E1、最佳混合、+Rerank 三个配置，在门槛集和对照集上各跑一遍，看两点：一是指标水平差多少，二是三个配置的排名是否一致 |
| 记录 | 生成阶段的 token 和费用（传 `token_usage_parser`，读 `total_tokens()` / `total_cost()`）；合格率；各合成器分别产出多少题 |
| 时间 | Ragas 接好之后做（m2-14 之后）。学习计划没有单列这一天，大约需要 2 小时 |

## 指标与门槛

| 层 | 指标 | 怎么算 | 什么时候跑 | 门槛 |
|---|---|---|---|---|
| 检索 | hit@5、recall@10、MRR、P50 延迟 | 自写的 `evals/p2-rag/recall.py`，按规则匹配，不调 LLM | 每一行实验 | 不设绝对值；混合 + Rerank 相对纯向量要有正提升 |
| 生成 | faithfulness | Ragas：把回答拆成若干陈述，逐条判断能否从检索到的片段推出 | 检查点 | **≥ 0.85** |
| 生成 | answer relevancy | Ragas：从回答反推出 3 个问题，算它们与原问题的 embedding 相似度；敷衍或拒答的回答直接记 0 | 检查点 | 只记录 |
| 检索（LLM 判） | context precision、context recall | Ragas：对照 `reference`，前者看有用的片段是否排在前面，后者看参考答案里的陈述有多少能在片段里找到 | 检查点 | 只记录，并与自写指标对照 |
| 拒答 | 无答案题拒答率 | Ragas 自定义指标，按规则判断，不调 LLM | 检查点 | **= 100%** |
| 拒答 | 可回答题误拒率 | 同上 | 检查点 | **≤ 10%**（42 题里最多 4 题） |

「检查点」指实验矩阵里 Ragas 一列打了 ✓ 的那些行。

**检索指标定义**（只在 42 道可回答题上算）

- 命中：检索结果与某个参考片段**来源相同**，且文本重叠率不低于阈值。阈值写在 `recall.py` 开头。
- hit@k：前 k 个结果里至少命中一个参考片段的题目，占全部题目的比例。
- recall@k：命中的参考片段数 ÷ 参考片段总数，按题平均。
- MRR：第一个命中结果的排名取倒数，按题平均；没命中记 0。

**口径**

- **faithfulness 和 answer relevancy 只算"可回答、且系统实际作答"的题。** 拒答在 Ragas 里拿不到有意义的分数：faithfulness 要么因为抽不出陈述而得 NaN，要么把拒答句当成"不被片段支持"的陈述，得分接近 0，具体取决于 judge；answer relevancy 则把"不知道"类回答当作敷衍，直接记 0。所以拒答（无论对错）都不进这两个指标，单独用拒答指标衡量。
- **context precision 和 context recall 在全部 42 道可回答题上算。** 它们衡量的是检索，系统拒不拒答都照算。
- **误拒率设上限，防止刷分。** 系统多拒几道难题，faithfulness 的样本里就只剩容易题，均值会虚高；给误拒率设上限，就堵住了这条路。
- **judge 固定。** judge 模型和生成模型分开配置，避免模型给自己打分；整个 M2 期间不换。judge 模型名和 Ragas 版本写进 `results.md` 的每一行。
- **门槛怎么判。** 最终配置连跑 3 次 Ragas，用均值判断是否达到门槛，同时报出 3 次里的最低值和最高值。如果给 judge 开了磁盘缓存（`cache=DiskCacheBackend()`），这 3 次要关掉，否则后两次读的都是缓存，测不出方差。
- **按题型拆开报。** 除了总分，再按事实、多片段、对比三类分别报。
- **注意样本小。** 42 道题里只要翻转 1 道，hit@k 就变化约 2.4 个百分点。比较两行结果时，同时报变好和变差的题数；只差一两道题，不下结论。
- **记录成本。** 每次跑 Ragas，都记下 judge 调用次数、token 和费用，M5 做 judge 校准时要用到。

**诊断：为什么召回了却答错**

| | faithfulness 高 | faithfulness 低 |
|---|---|---|
| **context recall 高** | 正常；再看 answer relevancy，确认回答切题 | 生成环节的问题：片段召回了，回答却越界发挥，或被无关片段带偏 → 调 prompt、片段顺序、top-k |
| **context recall 低** | 回答忠于片段，但片段不全，所以答得不完整 → 先修检索，也检查参考答案是否写得过宽 | 检索没召回，模型拿记忆补 → 先修检索，再收紧拒答阈值 |

**用到的 Ragas 能力**（按 0.4.3 核对）

| 能力 | 在 P2 里怎么用 |
|---|---|
| 核心指标 | `ragas.metrics.collections` 里的 `Faithfulness`、`AnswerRelevancy`、`ContextPrecision`、`ContextRecall`，用 `@experiment` 跑 |
| 自定义指标 | 用 `ragas.metrics` 的 `@discrete_metric` 写一个"拒答是否正确"指标，输出 pass / fail，按规则判断、不调 LLM：`none` 题拒答算 pass，其余题不拒答算 pass。再按题型汇总成拒答率和误拒率。Ragas 没有内置的拒答指标 |
| 测试集生成 | `TestsetGenerator`，用来生成对照集（见上一节） |
| 模型接入 | judge 用 `llm_factory` 加异步 client，走现有的模型网关。`AnswerRelevancy` 还要一个 embedding 模型，直接用检索用的那个多语言模型，因为问题是中文 |

**Ragas 版本与接入注意**（2026-10-30 核对）

- **锁定 `ragas==0.4.3`。** 这是 [PyPI](https://pypi.org/project/ragas/#history) 上的最新版，发布于 2026-01-13，之后再没有新版本。仓库已经迁到 [vibrantlabsai/ragas](https://github.com/vibrantlabsai/ragas)，有些 bug 报告长期无人回复。遇到问题先查 issue，必要时在本仓库里自己绕过去，不指望上游修复。
- **用 collections 指标配合 `@experiment`。** `evaluate()` 已标记为弃用。两套 API 不能混用：把 collections 指标传给 `evaluate()` 会报 `TypeError`。PyPI 页面上的 quickstart 在 0.4.3 上跑不通，不要照抄。具体写法见[实验文档](https://docs.ragas.io/en/stable/concepts/experimentation/)和 [0.3 → 0.4 迁移指南](https://docs.ragas.io/en/stable/howtos/migrations/migrate_from_v03_to_v04/)。
- **`@experiment` 会静默丢行。** 某一行报错时，它只打印一条警告就把这行丢掉；结果按完成顺序返回，不按输入顺序。所以每次跑完要核对行数，并按 `id` 对齐。另外，`retrieved_contexts` 为空时 `Faithfulness` 会直接报错，这样的行也会被丢掉。
- **judge 接入有两个坑。** 一是 client 必须是异步的（`AsyncOpenAI` / `AsyncAnthropic`）。二是 Ragas 默认同时传 `temperature` 和 `top_p`，走 Anthropic 接口时部分 Claude 模型会返回 400（[issue #2674](https://github.com/vibrantlabsai/ragas/issues/2674)），需要从 `llm.model_args` 里去掉 `top_p`，有的模型连 `temperature` 也要去掉（后者还没实测）。走 OpenAI 兼容接口时，网关要支持 JSON mode。
- **成本要自己记。** collections 指标配合 `@experiment` 这条路没有内置的 token 统计，需要在 client 层自己累计 usage。`TestsetGenerator` 可以直接传 `token_usage_parser`。
- **关掉匿名遥测**：设置 `RAGAS_DO_NOT_TRACK=true`。

## 实验矩阵

**原则**

- **逐项叠加**：每行只改一个变量，其余沿用当前最佳配置。不做全因子组合：5 种检索方式 × 是否 Rerank × 3 种分块器 × 6 组块大小与 overlap，共 180 组，对学习项目来说不值得。代价是看不到变量之间的交互，结论只对当前这套组合成立。
- **检索指标每行都跑**，因为确定、便宜。**Ragas 只在检查点跑**，因为要调 judge，既有费用又有方差。
- Milvus 和 ES 用**同一份 chunk、同一份 embedding 缓存**入库，这样两者的差异才能归因到检索方式本身。
- **固定项**：
  - 语料 commit、评测集版本；
  - embedding 模型：m2-04 选定后不再变，必须是多语言模型，候选为 bge-m3 和 Qwen3-Embedding；
  - 生成模型与 prompt、judge 模型；
  - 送入生成环节的片段数：top-5，到 E10 才调。

  默认分块方式：按标题切分，单块上限 512 token；过长的小节继续细分，细分时 overlap 15%。E7、E8 之后可能调整。

## 关键取舍

- **英文语料、中文提问**：贴近国内团队读英文文档的实际情况，也能把跨语言检索的问题暴露出来。代价是 BM25 只能靠英文术语命中，embedding 必须用多语言模型。
- **integrations 也入库**：多出一倍体量的相似页，检索更难，也更像真实的知识库。代价是入库和消融更慢，靠 embedding 缓存缓解。
- **自写检索指标与 Ragas 并存**：前者确定、便宜，每行都跑；后者更接近"答得对不对"，但有 judge 方差和费用，只在检查点跑。两者结论对不上的题，正好用来理解 Ragas 的口径。
- **拒答单独计量，并写成 Ragas 自定义指标**：无答案题不进 faithfulness 均值；所有指标在同一次评测里出结果，顺带学会 Ragas 的指标扩展接口。
- **门槛集手写，合成题只做对照**：门槛是否可信，不受合成题质量的影响；对照集用来回答"合成题能不能替代手写题做回归"。
- **逐项叠加，不做全因子**：理由见实验矩阵。
